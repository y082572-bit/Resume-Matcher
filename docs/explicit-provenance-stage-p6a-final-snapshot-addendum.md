# Explicit Provenance Stage P6-A: Final DOCX Snapshot Domain Addendum

## Purpose

This addendum adds a second, strictly additive capture contract on top of
Stage P6-A: `FinalDocxSnapshot`. It is not a replacement for
`ValidatedCvDocxSnapshot`, does not modify any existing P6-A module, and
does not implement SQL storage, a filesystem working-copy store, a
template, a DOCX renderer, a PDF converter, an API, a frontend, or a
local-open flow. Those all remain out of scope for this stage — see
`docs/explicit-provenance-stage-p6a.md` for the base P6-A / P6-B / P6-C
split, which this addendum does not change.

## Why `FinalDocxSnapshot` is additive, not a replacement

`ValidatedCvDocxSnapshot` (base P6-A) is built from the repository's own
current proposal slot, always structurally validated, and — when the raw
bytes differ from the pipeline's generated bytes — always gated on an
explicit `ManualDocumentSnapshotConfirmation`. It represents the
pipeline's own claim that a DOCX is *known-good enough to snapshot*.

`FinalDocxSnapshot` represents a different, narrower fact: "these were the
exact bytes of the Word working copy at the instant the user asked for a
PDF." It carries no opinion about whether those bytes are valid, whether
they match Truth Library facts, or whether the user's edits (if any) were
reviewed by anyone. Both contracts can coexist for the same owner and the
same underlying document lineage; neither one supersedes or feeds the
other. `ValidatedCvDocxSnapshot` stays exactly as it was before this
addendum — legacy in the sense that it is untouched, not in the sense that
it is deprecated.

## No validation semantics

`FinalDocxSnapshot` never carries a `structural_validation_result`, a
`validation_policy_version`, or any other validation-shaped field. The
finalization builder (`finalize_current_docx_for_pdf`) never calls a
`DocxStructuralValidator`, never performs semantic validation, and never
consults the Truth Library. A `FinalDocxSnapshot` existing for an owner is
not evidence that the DOCX is well-formed OOXML, that its content matches
any approved fact, or that it will render successfully.

## No manual confirmation

There is no confirmation object, no `CONFIRMED` decision, and no gate on
`edited_by_user=True`. Finalization always proceeds once the source
capture's binding checks out — an edited working copy is finalized exactly
as readily as an untouched one. The system never asks the user to confirm
their own edits before finalizing, because finalization is not an
assertion that the edits are correct.

## The user is responsible for Word edits

Everything about `FinalDocxSnapshot` follows from one policy decision:
once a proposal DOCX has been generated, what the user does to it in Word
before asking for a PDF is the user's own responsibility. The system
records the fact of an edit (`edited_by_user`) for the user's own
reference; it does not review, gate, or second-guess the edit.

## `edited_by_user` is report metadata, not a gate

`edited_by_user` is a plain, independently re-derivable boolean:
`generated_proposal_sha256 != final_docx_sha256`. `FinalDocxSnapshot`'s own
model validator enforces this equality — a `FinalDocxSnapshot` claiming
`edited_by_user=True` while the two hashes match (or vice versa) fails to
construct. It is surfaced purely so a caller can *report* "this PDF was
generated from an edited document" — it never blocks
`finalize_current_docx_for_pdf`, never requires a confirmation, and is
explicitly excluded from `final_snapshot_fingerprint` (see below) because
it is fully derived from fields the fingerprint already covers.

## A separate `FinalDocxSourceReader`

`FinalDocxSourceReader` (`cv_document_final_source_reader.py`) is a new,
separate Protocol — it does not extend, wrap, or get implemented by
anything in base P6-A. It abstracts "read the current Word working copy"
without this stage ever touching a filesystem: no path is ever accepted as
an argument or returned in a result, and this stage ships no concrete
(real) reader — only the Protocol, the `FinalDocxSourceCapture` model, and
the closed `WorkingCopyReadResult`/`WorkingCopyReadStatus` result types.

## A separate `FinalDocxSnapshotRepository`

`FinalDocxSnapshotRepository` (`cv_document_final_snapshot_repository.py`)
is likewise a new, separate Protocol with its own in-memory
implementation. It is never implemented by, and never shares storage
with, `CvDocumentArtifactRepository`. It has no "current slot" concept at
all — every save is an immutable, content-addressed metadata + bytes
record; nothing here ever gets superseded or CAS-replaced.

## Metadata identity vs. bytes identity

The repository maintains two independent lookups:

- **Metadata** (`FinalDocxSnapshot`) is always looked up by
  `final_snapshot_fingerprint` — never by a bytes hash.
- **Raw bytes** are always looked up by `final_docx_sha256` — never
  associated back to a single "owning" metadata record.

Bytes are deduplicated: two different `FinalDocxSnapshot` metadata records
(different owner/proposal lineage) may point at byte-identical DOCX
content, and the repository stores that payload exactly once. Given only
a bytes hash, there is no method that returns "some" metadata record for
it — the repository never picks an arbitrary lineage on the caller's
behalf.

## Trusted source binding — no separate caller-supplied baseline hash

The single most important invariant in this addendum: a caller can never
pass a `generated_proposal_sha256` into `finalize_current_docx_for_pdf` —
the parameter does not exist. The *only* trusted source for that baseline
is `FinalDocxSourceCapture.generated_proposal_sha256`, returned by
`source_reader.read_finalization_source(...)` alongside the raw bytes in
the same call. Before trusting anything on that capture, the builder
independently:

1. recomputes `owner_key_fingerprint` from the caller's own `owner_key`
   fields (never trusts `owner_key.owner_key_fingerprint` at face value),
2. compares it against `capture.owner_key_fingerprint`,
3. compares `capture.source_proposal_artifact_fingerprint` against the
   caller's `expected_proposal_artifact_fingerprint`,
4. compares `capture.source_proposal_revision` against the caller's
   `expected_proposal_revision`.

Any mismatch is fail-closed (`WORKING_COPY_BINDING_MISMATCH`) — the
finalization never proceeds on an unbound or mis-bound capture, and the
source reader is called exactly once per `finalize_current_docx_for_pdf`
invocation (no retry, no second read to "double check").

## No SQL in Stage A

This addendum, like base P6-A, ships zero SQL: no ORM model, no
migration, no schema-preflight change. `InMemoryFinalDocxSnapshotRepository`
is the only implementation, intended for tests and as the exact contract a
future SQL/filesystem-backed implementation must satisfy.

## No PDF conversion in Stage A

`finalize_current_docx_for_pdf` produces a `FinalDocxSnapshot` and nothing
else — it never calls a PDF conversion adapter, never produces PDF bytes,
and never touches `ConfirmedCvPdfArtifact` or the P6-A PDF slot. Turning a
`FinalDocxSnapshot` into an actual PDF is out of scope here.

## What comes next: Stage B

A future Stage B is expected to add a real filesystem-backed
`FinalDocxSourceReader` (reading the user's actual Word working copy), a
real `FinalDocxSnapshotRepository` implementation, and the PDF-generation
step that consumes a `FinalDocxSnapshot`. None of that exists yet — this
addendum defines only the domain contracts and their in-memory proof.
